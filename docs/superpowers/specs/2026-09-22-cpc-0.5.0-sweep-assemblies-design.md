# CPC 0.5.0 Sweep Assemblies Design

## Purpose

CPC 0.5.0 introduces **Sweep Assemblies**: a first-class CPC construction layer that groups multiple complete profiles into one reusable cross-section arrangement and applies that arrangement across one or many scene paths.

The design is informed by the useful separation observed in Home Builder 5.2.4 between profile packages, path discovery, and generated sweeps, but CPC will implement a general architectural-profile system rather than cabinet-specific logic.

The target product hierarchy becomes:

```text
primitive / component
→ complete profile
→ sweep assembly member
→ sweep assembly
→ sweep instance
→ generated sweep children
```

The 0.4.4 transform/connectivity release is the required foundation. Sweep Assemblies reuse CPC's canonical complete-profile placement state rather than introducing a second transform model.

## Goals

0.5.0 must allow a user to:

- combine two or more complete CPC profiles into a reusable Sweep Assembly;
- create an assembly visually from profiles arranged in the profile plane;
- preserve each member as an independently editable CPC profile variant;
- edit one member while the other assembly members remain visible as locked context;
- Recommit the edited member back into the assembly working copy;
- continue adjusting member placement and then Recommit the entire assembly;
- apply one assembly to multiple selected Curve paths in one operation;
- keep generated sweep children associated with their assembly definition and source path;
- refresh existing assembly instances after an assembly is recommitted;
- save/load a portable, self-contained `.cpcassembly` document;
- protect User Profile presets from accidental modification.

## Non-goals for 0.5.0

The first Sweep Assemblies release will not attempt to become a room, cabinet, wall, or architectural constraint solver.

Specifically deferred:

- automatic cabinet or room perimeter discovery;
- automatic toe-kick, appliance, wall, island, or corner-cabinet interpretation;
- proximity-based path discovery across arbitrary scene geometry;
- automatic live regeneration from every depsgraph change;
- path-role systems such as CROWN / BASE / PANEL;
- collection-wide rule systems;
- cross-file cloud or network libraries;
- implicit synchronization back to source User Profiles.

Those may be considered later only after the core assembly model is proven.

## Terminology

### User Profile preset

A reusable `.cpcprofile` document from CPC's existing User Profiles library.

A User Profile may be used as a source when adding a member to an assembly, but it never remains a live dependency.

### Assembly Definition

The authoritative reusable Sweep Assembly document. It owns:

- assembly ID;
- name and optional metadata;
- ordered member records;
- each member's embedded profile payload;
- each member's relative placement;
- optional source provenance.

### Assembly Member

One profile within an Assembly Definition.

Each member has a stable `member_id`, an embedded complete-profile payload, relative placement, enabled state, display name, and optional provenance.

### Embedded Profile Payload

The member's authoritative profile document stored inside the assembly.

It must contain enough information to reconstruct the complete profile without access to the source User Profile library.

### Source Provenance

Optional information recording where a member originally came from, such as:

- source preset ID;
- source preset name;
- source profile type;
- source authority hash;
- optional source library reference.

Provenance is descriptive only. It never grants write authority.

### Assembly Working Copy

Temporary editable assembly state created by **Edit Assembly**.

Changes remain local to the working copy until **Recommit Assembly**.

### Sweep Instance

A scene-level application of one Assembly Definition to one or more source paths.

### Sweep Child

One generated swept Curve corresponding to one Assembly Member on one source path.

## Core authority rule

### Embedded member payloads are authoritative

Once a profile is added to an assembly, CPC copies the complete usable profile payload into the assembly.

From that point onward:

```text
source User Profile
        ↓ copy / instantiate
embedded Assembly Member payload
        ↓
assembly editing authority
```

The source User Profile is not live-linked.

Ordinary assembly operations must never write to the source preset:

- Edit Member Profile;
- Recommit Profile;
- member Offset/Rotation/Scale edits;
- Recommit Assembly;
- Refresh Assembly Instances;
- save/reload of the Blender file.

This is a hard safety invariant.

## Source-preset update policy

Updating the source User Profile is a separate explicit action.

The member editor may expose:

- **Save as New User Profile**
- **Update Source User Profile…**
- **Reload from Source…**

### Save as New User Profile

This is the preferred/default export path.

It creates a new `.cpcprofile` from the current embedded member variant and leaves the original preset untouched.

### Update Source User Profile…

This is intentionally secondary and requires explicit confirmation.

Before writing, CPC must identify:

- Assembly name;
- member name;
- source preset name/ID;
- whether the source has changed since the member was instantiated.

The confirmation UI should present **Save as New Profile** as the safer primary choice and overwrite as the deliberate secondary choice.

### Reload from Source…

Reload is destructive to the assembly-local member variant and therefore also requires confirmation.

The operation replaces the member's embedded profile payload with a fresh copy of the chosen source preset while preserving or explicitly resetting member placement according to the user's choice.

## Nested editing model

Sweep Assembly editing is hierarchical.

```text
Edit Assembly
    ↓
assembly working copy
    ↓
select member
    ↓
Edit Member Profile
    ↓
normal CPC parametric profile editing
    ↓
Recommit Profile
    ↓
return to assembly working copy
    ↓
adjust relative member placement
    ↓
Recommit Assembly
    ↓
assembly definition becomes authoritative
    ↓
refresh instances
```

### Edit Assembly

Edit Assembly opens the current assembly in an isolated profile-plane authoring context.

All members are visible.

The selected member may be transformed through CPC semantic controls. Non-selected members remain locked visual context.

### Edit Member Profile

Editing one member restores that member's embedded PARAMETRIC construction recipe when available.

Other members remain visible but are non-editable context. The UI should visually distinguish the actively edited member from ghosted/locked assembly members.

### Recommit Profile

Recommit Profile updates only the embedded payload for that Assembly Member.

It must preserve:

- `member_id`;
- assembly-relative placement;
- member ordering;
- enabled state;
- source provenance;
- assembly working-copy identity.

It must not update the User Profile library.

After Recommit Profile, CPC returns to the parent Assembly Edit session rather than exiting assembly editing.

### Cancel Member Edit

Cancel restores the member payload that existed when Edit Member Profile began and returns to the Assembly Editor.

### Recommit Assembly

Recommit Assembly makes the working-copy member set and placements authoritative.

It then refreshes scene instances associated with that assembly.

### Cancel Assembly Edit

Cancel restores the entire assembly state that existed when Edit Assembly began.

No generated scene instance should be altered merely because an assembly edit was started and later cancelled.

## Member placement model

Assembly-relative placement uses the same conceptual state introduced for complete profiles in 0.4.4:

- Offset X;
- Offset Y;
- Rotation;
- Flip X;
- Flip Y;
- Uniform Scale.

The conceptual composition remains:

```text
embedded canonical member geometry
→ member uniform scale
→ member flip
→ member rotation
→ member profile-local offset
→ source path frame
```

Interaction order must not become transform order.

Assembly member placement must not accumulate arbitrary Blender Object transforms as a second authority.

## Visual assembly authoring

A primary workflow is **Create Assembly from Selected Profiles**.

The user may:

1. create or load several complete profiles;
2. arrange them visually in the profile plane;
3. select the profiles;
4. invoke **Create Sweep Assembly**.

CPC extracts each profile's canonical visible result and relative profile-plane placement into member records.

The resulting assembly must be reconstructable without keeping the temporary authoring objects.

## Assembly persistence

### File format

Introduce a new self-contained portable document:

```text
.cpcassembly
```

This is separate from `.cpcprofile` so existing User Profile format v1 remains stable.

Proposed top-level shape:

```json
{
  "format": "CPC_SWEEP_ASSEMBLY",
  "format_version": 1,
  "id": "assembly-uuid",
  "name": "Traditional Crown",
  "description": "",
  "members": []
}
```

Each member conceptually contains:

```json
{
  "member_id": "member-uuid",
  "name": "Crown",
  "enabled": true,
  "profile": {
    "profile_type": "PARAMETRIC",
    "geometry": {},
    "recipe": {}
  },
  "placement": {
    "offset_x": 0.018,
    "offset_y": 0.082,
    "rotation": 0.0,
    "flip_x": false,
    "flip_y": false,
    "uniform_scale": 1.0
  },
  "source": {
    "preset_id": "",
    "preset_name": "",
    "authority_hash": ""
  }
}
```

The exact schema will be implemented through a validator module rather than ad-hoc dictionary access.

### Self-contained requirement

A valid `.cpcassembly` must reconstruct every member without requiring:

- the original User Profile files;
- the original Blender scene;
- external profile objects.

Source provenance may be missing or stale without invalidating the assembly.

## Reusing profile serialization

0.5.0 should not invent a second incompatible way to serialize profile geometry and recipes.

The existing User Profile pipeline already has:

- normalized curve geometry snapshots;
- PARAMETRIC vs STATIC classification;
- recipe schema/version data;
- authority hashing;
- validated preset loading.

Implementation should extract or expose reusable profile-payload helpers from the User Profile subsystem so `.cpcprofile` and `.cpcassembly` member payloads share the same profile semantics.

## Scene object model

Generated assembly data must use stable identifiers rather than object names as authority.

Suggested scene metadata:

### Assembly controller

- `cpc_sweep_assembly` = true
- `cpc_assembly_id`
- `cpc_assembly_instance_id`

### Source path relationship

- `cpc_source_path_id`
- `cpc_assembly_instance_id`

### Generated sweep child

- `cpc_assembly_id`
- `cpc_assembly_instance_id`
- `cpc_assembly_member_id`
- `cpc_source_path_id`
- `cpc_sweep` = true

Names remain user-facing only.

## Multiple selected paths

0.5.0 extends the current single-profile/single-selected-Curve workflow.

For one assembly with M enabled members applied to N selected paths, CPC creates up to:

```text
M × N generated sweep children
```

Each child uses:

- the corresponding embedded member profile;
- the member's canonical assembly-relative placement;
- the source path;
- the existing CPC sweep settings for 2D/3D mode, Caps, smoothing, twist, and path resolution.

The operation must support multiple Curve objects in Object Mode.

Existing **Single Profile** sweep behavior remains available and unchanged.

## Instance refresh model

Generated instances are explicit relationships, not anonymous output.

Recommit Assembly may refresh instances that reference that assembly ID.

Refresh must:

- update CPC-owned generated children only;
- preserve source paths;
- preserve unrelated scene geometry;
- preserve stable instance IDs where practical;
- remove obsolete CPC-owned member children when members are removed/disabled;
- create missing member children;
- update profile bevel relationships and sweep settings.

0.5.0 should not perform automatic depsgraph-wide live refresh for every edit.

A deliberate commit/refresh boundary is safer and avoids expensive room-wide rebuilding during profile editing.

## UI direction

### Sweep mode

The Sweep panel gains an explicit mode:

```text
Mode
(o) Single Profile
( ) Sweep Assembly
```

Single Profile preserves the current 0.4.4 controls.

Assembly mode exposes:

- active assembly;
- Edit Assembly;
- New Assembly;
- Apply Assembly to Selected Curves;
- Refresh Instances;
- shared Sweep Settings.

### Assembly Editor

The editor shows ordered members and selected-member placement.

Conceptual controls:

```text
Assembly: Traditional Crown

Members
✓ Spacer
✓ Crown
✓ Cove

[ Edit Member Profile ]

Member Placement
Offset X
Offset Y
Rotation
Uniform Scale
Flip X
Flip Y

[ Add Active Profile ]
[ Remove Member ]

[ Recommit Assembly ]
[ Cancel Assembly Edit ]
```

Source-preset actions belong in a secondary area, not next to ordinary Recommit.

## Compatibility

0.5.0 must preserve:

- `.cpcprofile` format v1;
- recipe schema 11+;
- transform schema 1;
- PARAMETRIC and STATIC profile classes;
- 0.4.4 canonical profile placement;
- in-place complete-profile Recommit behavior;
- existing single-profile Sweep;
- User Profile Categories/Search/indexing;
- custom User Profile library path behavior;
- explicit endpoint connectivity semantics;
- 2D Caps / Fill Mode semantics;
- lazy viewport overlay handlers.

No 0.4.x file needs migration merely to open in 0.5.0.

## Failure and safety rules

- Missing source presets never invalidate an assembly because the embedded member payload is authoritative.
- Invalid embedded member payloads fail validation with member-specific errors.
- Recommit Member never writes to library files.
- Recommit Assembly never writes to library files.
- Refresh Instances never edits source paths.
- Updating or reloading from a source preset requires explicit confirmation.
- Member IDs and assembly IDs are not derived from object names.
- Deleting generated sweep children does not delete the assembly definition or source preset.
- Deleting an assembly definition with live instances requires a clear choice about whether generated instances are retained, detached, or removed.

## 0.5.0 release acceptance

The milestone is accepted when all of the following are true:

1. A two-member assembly can be created visually from complete CPC profiles.
2. The assembly stores self-contained embedded member payloads.
3. Deleting or changing the original source User Profiles does not change the assembly.
4. A PARAMETRIC member can be reopened, edited, Recommitted, and returned to the parent Assembly Editor.
5. Other members remain visible as non-editable context while one member is edited.
6. Member Recommit preserves member identity and assembly-relative placement.
7. Assembly Cancel restores the complete pre-edit state.
8. Recommit Assembly updates the authoritative assembly and refreshes its scene instances.
9. One assembly can be applied to multiple selected Curve paths in one operation.
10. Generated sweep children retain stable assembly/member/path relationships.
11. Single Profile Sweep remains behaviorally compatible with 0.4.4.
12. `.cpcassembly` save/load round-trips PARAMETRIC and STATIC members.
13. Ordinary assembly editing never modifies User Profile preset files.
14. **Save as New User Profile** creates a separate preset from an assembly member.
15. **Update Source User Profile…** cannot occur without explicit confirmation.
16. Automated tests cover schema validation, profile-payload authority, nested editing state, instance planning, and non-destructive source-preset behavior.
17. Production Blender validation passes with representative two-member and three-member architectural assemblies.

## Later extensions

After the core model is stable, possible follow-up work includes:

- assembly thumbnails and indexed library browsing;
- Path Roles such as CROWN / BASE / PANEL;
- apply-to-collection and tagged-path workflows;
- assembly variants;
- selective member refresh;
- optional source-difference comparison UI;
- controlled live refresh;
- scene-wide trim packages;
- higher-level architectural path discovery.
